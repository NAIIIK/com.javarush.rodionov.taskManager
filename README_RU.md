# Task Manager

REST API для управления задачами в стиле Jira/Trello на Spring Boot. Пользователи
создают проекты, приглашают участников с ролями, ведут задачи по фиксированному
workflow и оставляют комментарии - всё под защитой JWT-аутентификации.

## Возможности

- **JWT-аутентификация** - регистрация/логин, access + refresh токены, ротация и
  отзыв refresh-токена, logout.
- **Глобальные роли** - каждый пользователь либо `USER`, либо `ADMIN`. Регистрация
  всегда создаёт `USER`; роль `ADMIN` никак не выдаётся через API и открывает
  доступ только к management-эндпоинтам `/actuator/**` (см. [Переменные
  окружения](#переменные-окружения) / [Демо-данные](#демо-данные-seed-миграция) -
  как получить админа локально).
- **Проекты** - любой зарегистрированный пользователь может создать проект и
  автоматически становится его владельцем. Проект можно переименовать/изменить
  описание и удалить (только владелец, удаление каскадное - вместе с участниками,
  задачами и комментариями).
- **Роли внутри проекта** (не глобальные):
  - `OWNER` - полный контроль: изменение/удаление проекта, управление ролями
    участников, плюс всё, что может `MANAGER`. Ровно один на проект, назначается
    при создании, через API не передаётся другому пользователю.
  - `MANAGER` - создаёт/изменяет/удаляет задачи, добавляет/удаляет участников,
    модерирует комментарии. Не может удалить проект или менять чужие роли.
  - `MEMBER` - работает над задачами, может назначить на себя любую задачу проекта.
- **Управление участниками проекта** - добавить существующего пользователя по email
  с ролью (только `MANAGER`/`MEMBER`), посмотреть список участников, сменить роль
  участника, удалить участника (владельца через этот эндпоинт удалить или
  переназначить роль нельзя).
- **Задачи** - фиксированный набор статусов (`TO_DO` → `IN_PROGRESS` →
  `IN_CODE_REVIEW` → `DONE`), приоритет (`LOW`/`MEDIUM`/`HIGH`), опциональные дедлайн
  и исполнитель (это `ProjectMember`, а не `User`). Полный CRUD плюс отдельный
  эндпоинт самоназначения; статус может менять исполнитель либо `OWNER`/`MANAGER`.
- **Комментарии** к задачам - создание, список, редактирование и удаление;
  редактировать/удалять может автор или `OWNER`/`MANAGER` (модерация).
- **Интерактивная документация API** - спецификация OpenAPI 3 и Swagger UI,
  генерируются автоматически из кода (springdoc).
- **Логирование через AOP** - каждый вызов метода `@Service` логируется (аргументы,
  результат, время выполнения, исключения). Чувствительные данные (пароли, токены)
  маскируются через кастомные аннотации `@Sensitive` / `@SensitiveResult` и никогда
  не попадают в лог в открытом виде.
- **Централизованный сбор логов** - в Docker логи приложения отправляются через
  ELK-стек (Elasticsearch, Logstash, Kibana) для поиска и фильтрации.
- **Единая обработка исключений** через `@RestControllerAdvice` - консистентные
  JSON-ответы об ошибках со статусом, сообщением, временем и путём запроса.

## Стек технологий

| Слой             | Технология                                                                                        |
|------------------|---------------------------------------------------------------------------------------------------|
| Язык             | Java 21                                                                                           |
| Фреймворк        | Spring Boot (Web MVC, Security, Data JPA, AOP, Validation, Actuator)                              |
| База данных      | PostgreSQL, миграции через Liquibase                                                              |
| Аутентификация   | JWT (`jjwt`), access + refresh токены                                                             |
| Документация API | OpenAPI 3 / Swagger UI (`springdoc-openapi`)                                                      |
| Сборка           | Maven                                                                                             |
| Логирование      | SLF4J + Logback (`logback-spring.xml`), кастомный AOP-аспект логирования                          |
| Доставка логов   | ELK-стек (Elasticsearch, Logstash, Kibana) + Filebeat, JSON-логи через `logstash-logback-encoder` |
| Тесты            | JUnit 5, Mockito (unit), Testcontainers + PostgreSQL (интеграционные)                             |
| Контейнеры       | Docker, Docker Compose (app, Postgres, pgAdmin, ELK-стек)                                         |

## Структура проекта

Код организован **feature-first** (пакет на фичу - entity, репозиторий, сервис,
контроллер, DTO лежат вместе), а не по слоям:

```
com.javarush.taskmanager
├── auth/               регистрация, логин, refresh, logout
├── user/               сущность пользователя, глобальная роль
├── project/            проекты
│   └── member/         участники проекта, роли, проверка доступа
├── task/               задачи
├── comment/            комментарии к задачам
├── security/           JWT-сервис, фильтры, определение текущего пользователя
├── logging/            AOP-аспект логирования + @Sensitive/@SensitiveResult
├── exception/          кастомные исключения + глобальный обработчик ошибок
└── config/             конфигурация security и web
```

## Запуск

### Через Docker Compose (рекомендуется)

Скопируйте шаблон переменных окружения и при необходимости поправьте значения:

```bash
cp .env.example .env
```

Затем поднимите всё:

```bash
docker compose up --build
```

Поднимутся:

| Сервис        | URL                   | Комментарий                                                             |
|---------------|-----------------------|-------------------------------------------------------------------------|
| app           | http://localhost:8080 | само приложение                                                         |
| pgAdmin       | http://localhost:5050 | логин `admin@taskmanager.com` / `admin`                               |
| Kibana        | http://localhost:5601 | интерфейс поиска по логам, см. [Логирование](#логирование-и-сбор-логов) |
| Elasticsearch | http://localhost:9200 | хранилище логов, без авторизации в dev-конфигурации                     |
| Logstash      | tcp/5044 (внутренний) | принимает логи от Filebeat                                              |
| PostgreSQL    | localhost:5432        | –                                                                       |

### Локально

Нужны Java 21 и запущенный PostgreSQL, соответствующий
`src/main/resources/application.yaml` (или переопредели через переменные окружения).

```bash
./mvnw spring-boot:run
```

При локальном запуске (без активного профиля `docker`) стек ELK и JSON-логирование
не используются вовсе - логи идут обычным текстом в консоль + файл, см.
[Логирование](#логирование-и-сбор-логов).

### Переменные окружения

Задаются в `.env` (скопируйте из `.env.example`), используются в `docker-compose.yaml`:

| Переменная                 | Описание                                 | Значение в `.env.example` |
|----------------------------|------------------------------------------|---------------------------|
| `JWT_SECRET`               | Секрет для подписи access-токенов (HMAC) | небезопасная dev-заглушка |
| `POSTGRES_USER`            | Пользователь БД                          | `postgres`                |
| `POSTGRES_PASSWORD`        | Пароль БД                                | `postgres`                |
| `PGADMIN_DEFAULT_EMAIL`    | Эл. почта pgAdmin                        | `admin@taskmanager.com`   |
| `PGADMIN_DEFAULT_PASSWORD` | Пароль pgAdmin                           | `admin`                   |

### Демо-данные (seed-миграция)

`db/changelog/changes/007-seed-fake-data.yaml` (запускается автоматически
Liquibase-ом при старте, в любом окружении) добавляет набор фейковых сущностей,
чтобы сразу после `docker compose up` было что посмотреть, не регистрируясь вручную:

- 1 пользователь-админ и 9 обычных пользователей (email вида `@taskmanager.local`)
- 3 проекта, в каждом по одному `OWNER`, одному-двум `MANAGER` и нескольким `MEMBER`
- ~15 задач вперемешку по всем статусам/приоритетам и несколько комментариев

Логины/пароли для сидовых аккаунтов:

| Пользователь                                            | Пароль        | Глобальная роль |
|---------------------------------------------------------|---------------|-----------------|
| `admin@taskmanager.local`                               | `admin`       | `ADMIN`         |
| остальные (например, `alice.johnson@taskmanager.local`) | `password123` | `USER`          |

Это фикстуры только для локальной разработки/демо.

## Обзор API

Все эндпоинты, кроме `/api/auth/**`, требуют валидный access-токен
(`Authorization: Bearer <token>`).

### Интерактивная документация (Swagger)

После запуска приложения полное интерактивное описание API доступно по адресам:

- Swagger UI: `http://localhost:8080/swagger-ui.html`
- Сырая спецификация OpenAPI 3: `http://localhost:8080/v3/api-docs`

Это первоисточник по форматам запросов/ответов, правилам валидации и кодам
статусов - таблицы ниже дают только общую карту, а не полный контракт.

### Auth - `/api/auth`

| Метод | Путь        | Описание                             |
|-------|-------------|--------------------------------------|
| POST  | `/register` | Создать аккаунт пользователя         |
| POST  | `/login`    | Получить access + refresh токены     |
| POST  | `/refresh`  | Обменять refresh-токен на новую пару |
| POST  | `/logout`   | Отозвать refresh-токен               |

### Проекты - `/api/projects`

| Метод  | Путь           | Описание                                                                        |
|--------|----------------|---------------------------------------------------------------------------------|
| POST   | `/`            | Создать проект (создатель становится `OWNER`)                                   |
| GET    | `/`            | Список проектов, в которых состоит пользователь                                 |
| GET    | `/{projectId}` | Получить один проект (только участники)                                         |
| PATCH  | `/{projectId}` | Изменить название/описание (только `OWNER`)                                     |
| DELETE | `/{projectId}` | Удалить проект каскадно - с участниками/задачами/комментариями (только `OWNER`) |

### Участники проекта - `/api/projects/{projectId}/members`

| Метод  | Путь          | Описание                                                                                 |
|--------|---------------|------------------------------------------------------------------------------------------|
| POST   | `/`           | Добавить существующего пользователя по email с ролью (`MANAGER`+; `OWNER` выдать нельзя) |
| GET    | `/`           | Список участников проекта (только участники)                                             |
| PATCH  | `/{memberId}` | Сменить роль участника (только `OWNER`; роль владельца менять нельзя)                    |
| DELETE | `/{memberId}` | Удалить участника (`MANAGER`+; владельца удалить нельзя)                                 |

### Задачи - `/api/projects/{projectId}/tasks`, `/api/tasks/{taskId}`

| Метод  | Путь                              | Описание                                                                              |
|--------|-----------------------------------|---------------------------------------------------------------------------------------|
| POST   | `/api/projects/{projectId}/tasks` | Создать задачу (`OWNER`/`MANAGER`)                                                    |
| GET    | `/api/projects/{projectId}/tasks` | Список задач проекта (участники)                                                      |
| PATCH  | `/api/tasks/{taskId}/assign-self` | Назначить задачу на себя (любой участник проекта)                                     |
| PATCH  | `/api/tasks/{taskId}/status`      | Изменить статус задачи (исполнитель либо `OWNER`/`MANAGER`)                           |
| PATCH  | `/api/tasks/{taskId}`             | Частично обновить название/описание/приоритет/исполнителя/дедлайн (`OWNER`/`MANAGER`) |
| DELETE | `/api/tasks/{taskId}`             | Удалить задачу вместе с комментариями (`OWNER`/`MANAGER`)                             |

### Комментарии - `/api/tasks/{taskId}/comments`

| Метод  | Путь           | Описание                                                                |
|--------|----------------|-------------------------------------------------------------------------|
| POST   | `/`            | Добавить комментарий к задаче (участники)                               |
| GET    | `/`            | Список комментариев к задаче (участники)                                |
| PATCH  | `/{commentId}` | Отредактировать комментарий (автор, либо `OWNER`/`MANAGER` - модерация) |
| DELETE | `/{commentId}` | Удалить комментарий (автор, либо `OWNER`/`MANAGER` - модерация)         |

Про исполнителя: `assigneeId` у задачи - это всегда id записи `ProjectMember`
(участия в проекте), а не id `User`, и он должен принадлежать тому же проекту.

## Логирование и сбор логов

Логирование настроено в `logback-spring.xml` и ведёт себя по-разному в зависимости
от активного Spring-профиля:

- **Локальный запуск / из IDE** (профиль `docker` **не** активен) - обычный
  текстовый вывод в консоль плюс файл с ротацией `${LOG_PATH}/task-manager.log`,
  ротация раз в день и при превышении 50 МБ, история хранится 14 дней (общий
  лимит - 1 ГБ).
- **Профиль `docker`** - логи пишутся структурированным **JSON** (через
  `logstash-logback-encoder`) только в stdout.

### Быстрый доступ к консольным логам

Если нужно быстро глянуть логи, не открывая Kibana - проще всего смотреть stdout
контейнера напрямую:

```bash
docker compose logs -f app
```

- `-f` (follow) - показывает новые строки по мере появления, аналог `tail -f`.
- Без `-f` команда выведет всё, что накопилось на данный момент, и завершится.
- `--tail=100` - показать только последние 100 строк перед тем, как перейти в
  режим слежения:
  ```bash
  docker compose logs -f --tail=100 app
  ```
- При локальном запуске (`./mvnw spring-boot:run`) логи и так идут прямо в консоль
  IDE/терминала - дополнительная команда не нужна.

Это самый быстрый способ проверить, что приложение стартовало корректно, или
посмотреть, как проходит конкретный запрос. Kibana (ниже) нужна, когда требуется
искать за более длительный период или фильтровать по полям вроде уровня лога или
имени логгера.

### ELK-стек (только в Docker)

При запуске через `docker compose` stdout контейнера забирается и прогоняется
через ELK-пайплайн, чтобы логи можно было искать, а не грепать руками:

```
app (stdout, JSON) → Filebeat → Logstash → Elasticsearch → Kibana
```

- **Filebeat** автообнаруживает контейнер `taskmanager-app` и читает его лог-файл
  Docker.
- **Logstash** (`elk/logstash/pipeline/logstash.conf`) разбирает JSON-содержимое и
  пишет его в Elasticsearch в ежедневный индекс `taskmanager-app-YYYY.MM.dd`.
- **Kibana** (`http://localhost:5601`) - здесь логи и просматриваются: создайте
  data view с паттерном индекса `taskmanager-app-*` и полем времени `@timestamp`
  в *Stack Management → Data Views*, затем используйте *Discover* для поиска и
  фильтрации.

Эта dev-конфигурация запускает Elasticsearch/Kibana с отключённой безопасностью
(`xpack.security.enabled: false`) - логин не требуется.

Поверх всего этого `logging.LoggingAspect` оборачивает каждый метод `@Service` и
логирует:

```
--> AuthService.login(***)
<-- AuthService.login [12 ms] returned ***
```

Аргументы, помеченные `@Sensitive`, и результаты методов с `@SensitiveResult`
маскируются (`***`) вместо вывода в лог - это касается паролей, access/refresh
токенов и любых DTO или объектов, которые их несут (`LoginRequest`,
`RegisterRequest`, `RefreshRequest`, `AuthResponse`, сырые JWT-строки,
`CustomUserDetails`).

## Тесты

```bash
./mvnw test
```

Unit-тесты (Mockito) покрывают сервисную логику изолированно; интеграционные тесты
(Testcontainers + реальный контейнер PostgreSQL) проверяют полные сценарии запросов
для auth, проектов, задач и комментариев.
